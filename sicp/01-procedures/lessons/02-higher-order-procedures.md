# 02. 계산의 공통된 모양을 함수로 표현하기

> **주제:** 고차 프로시저(Higher-order Procedures) · SICP 제2판 §1.3.1~§1.3.2  
> **선행:** 함수 정의, 재귀 호출, 매개변수 정도를 알면 시작할 수 있습니다.

## 이번에 탐구할 질문

1부터 5까지의 숫자를 모두 더한다고 해봅시다.

```text
1 + 2 + 3 + 4 + 5
```

이번에는 각 숫자의 제곱을 더해 봅시다.

```text
1² + 2² + 3² + 4² + 5²
```

두 문제는 다른 문제일까요? 각각 다른 코드를 작성할 수도 있습니다. 그런데 **더하는 작업은 그대로이고, 더하기 전에 숫자에 무엇을 하는지만** 달라졌습니다.

이런 공통점을 코드에서 어떻게 표현할 수 있을까요?

## 1. 먼저 두 함수를 작성해 보기

Scheme에서는 `(square 3)`이 `square(3)`과 비슷한 뜻입니다. `(+ 1 2)`는 `1 + 2`입니다.

```scheme
(define (square x) (* x x))

(define (sum-integers a b)
  (if (> a b)
      0
      (+ a (sum-integers (+ a 1) b))))

(define (sum-squares a b)
  (if (> a b)
      0
      (+ (square a) (sum-squares (+ a 1) b))))
```

잠깐 두 함수에서 **같은 부분**과 **달라지는 부분**을 직접 찾아보세요.

- 둘 다 `a > b`이면 0을 돌려줍니다.
- 둘 다 현재 숫자를 처리한 후 다음 숫자로 넘어갑니다.
- 한쪽은 `a`, 다른 쪽은 `(square a)`를 더합니다.

공통된 계산 과정은 유지하고 **숫자를 어떻게 처리할지만 밖에서 정할 수 있다면** 함수 하나로 두 문제를 모두 표현할 수 있습니다.

## 2. 함수를 다른 함수에 전달하기

```scheme
(define (sum term a next b)
  (if (> a b)
      0
      (+ (term a)
         (sum term (next a) next b))))

(define (identity x) x)
(define (inc x) (+ x 1))
(define (square x) (* x x))

(sum identity 1 inc 5) ; 15
(sum square 1 inc 5)   ; 55
```

여기서 `term`은 **각 숫자로부터 무엇을 더할지 결정하는 함수**, `next`는 **다음 숫자를 결정하는 함수**입니다.

처음 호출인 `(sum square 1 inc 3)`의 흐름을 보면:

```text
(sum square 1 inc 3)
→ (+ (square 1) (sum square 2 inc 3))
→ (+ 1 (square 2) (sum square 3 inc 3))
→ (+ 1 4 (square 3) (sum square 4 inc 3))
→ (+ 1 4 9 0)
→ 14
```

**정수를 더하는 방법과 제곱을 더하는 방법을 각각 구현한 것이 아니라, '무엇을 더할지'를 전달해 하나의 계산 구조를 재사용한 것입니다.**

이렇게 함수를 인자로 받거나 함수를 결과로 반환하는 함수를 **고차 프로시저(Higher-order Procedure)**라고 부릅니다.

### 함수 이름과 함수 호출은 다릅니다

`square`는 함수를 전달하는 것이고, `(square 3)`은 지금 계산해서 결과를 얻는 것입니다. 위의 `sum`에는 전자가 들어가야 합니다.

## 3. 한 번 더 추상화할 수 있을까?

숫자를 하나씩 더하는 것 대신, 하나씩 **곱하는** 계산을 만들 수도 있습니다.

```scheme
(define (product term a next b)
  (if (> a b)
      1
      (* (term a)
         (product term (next a) next b))))
```

이번에도 `sum`과 `product`는 꽤 비슷합니다. 달라진 것은 더하기와 곱하기, 그리고 계산을 시작할 때의 기본값(더하기는 0, 곱하기는 1)입니다.

그렇다면 **결과를 합치는 방법**도 밖에서 전달하면 어떨까요?

```scheme
(define (accumulate combine initial term a next b)
  (if (> a b)
      initial
      (combine (term a)
               (accumulate combine initial term (next a) next b))))
```

사용 예시:

```scheme
(accumulate + 0 identity 1 inc 5) ; 15
(accumulate * 1 identity 1 inc 5) ; 120
```

이때 중요한 질문은 **무엇이 바뀔 수 있고, 무엇은 그대로인지** 구분하는 것입니다.

- `combine`: 두 결과를 어떻게 합칠까?
- `initial`: 더 합칠 것이 없을 때 어떤 값을 반환할까?
- `term`: 현재 항목에서 무엇을 계산할까?
- `next`: 다음 항목으로 어떻게 이동할까?
- `a`, `b`: 어디서 시작하고 멈출까?

여러 함수를 하나로 합친 것보다 더 중요한 점은, **문제들에 공통으로 들어 있는 계산의 뼈대가 드러났다는 사실**입니다.

## 4. 추상화가 항상 좋을까?

고차 함수가 가능하다고 해서 언제나 `accumulate`처럼 일반화해야 하는 것은 아닙니다.

인자가 너무 많아지고 코드의 의도를 파악하기 어려워질 수 있기 때문입니다. 반대로 여러 문제에서 동일한 계산 구조가 반복될 때는 추상화를 통해 **무엇이 공통적이고 무엇이 달라지는지** 분명히 드러낼 수 있습니다.

다음 질문을 고민해 보세요.

> 서로 다른 세 문제를 함수 하나로 표현했다고 해서, 반드시 이해하기 쉬운 프로그램이 된 것일까요?

추상화는 코드 길이를 줄이는 기술이면서 동시에 **문제를 보는 관점을 바꾸는 방법**입니다. 하지만 지나친 일반화는 오히려 이해를 어렵게 할 수 있습니다.
